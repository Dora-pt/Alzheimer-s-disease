## 1. 分工原则

1. **6 人 6 角，一人主责**：每人一个主角色，避免「大家都在做需求、没人在写代码」。
2. **双人复核**：需求、设计、代码、测试四个环节都必须有第二人复核，不允许单人自审自签。
3. **阶段轮转**：角色固定，但工作量按阶段错峰（见第 3 节），高峰期跨角色支援。
4. **客户对接唯一出口**：只有项目经理和需求分析两人对老师发正式问题；其余人不私下改范围。
5. **工作量均衡**：每人每周投入 8–10 小时，迭代内人均 16–20 小时，人差不超过 ±25%；不允许有人负责「大而空」的任务，也不允许有人只在最后一周发力（见第 3.2、8 节）。
6. **产出可验证**：分工以「可指认的产出物」为单位认领，不接受「我负责协调」这类无法验证的职责。

## 2. 角色卡

### R1 项目经理兼配置管理员（PM / CM）

**核心职责**

- 制定并维护项目计划（WBS、里程碑、甘特图）、风险登记表
- 组织周会、跟踪任务看板、维护问题日 志
- 管理需求变更（谁提、评审、影响分析、批准、回写）
- 配置管理：Git 仓库、分支策略、版本基线（tag）、文档版本号
- 对客户（老师）的唯一汇报出口

**交付物**：项目计划、周报、风险登记表、变更记录、配置管理计划、交付清单
**关键节点**：第 1 周建库建档；每个里程碑打 tag；验收前组织内部预审

---

### R2 需求分析兼产品设计（BA / UX）

**核心职责**

- 需求获取：访谈老师、整理问题清单（承接 `01` 文档 Q1–Q14）
- 编写《需求规格说明书》《数据字典》，画数据流图、用例图
- 绘制界面原型（低保真 → 高保真），定义每张量表的录入页布局
- 编写《用户手册》初稿（课程生命周期要求）
- 维护需求跟踪矩阵（需求 → 设计 → 代码 → 测试用例）

**交付物**：需求规格说明书、数据字典、原型、用例图、跟踪矩阵
**关键节点**：第 2 周冻结需求基线 v1.0；设计阶段全程配合澄清
**技能**：文档写作、医学量表理解、原型工具（Figma / Axure / 墨刀任选）

---

### R3 架构与技术负责人（TA）

**核心职责**

- 技术选型（前端框架、后端框架、数据库、部署方式），给出 2–3 方案对比与决策记录
- 总体设计：系统架构图、模块划分、接口设计、数据库设计（E-R 图）
- 详细设计：关键流程时序图、HIPO/PDL（课程生命周期要求）
- 制定编码规范，主持代码评审，控制技术风险
- 解决开发中的技术难题（图片展示、计时器、语音接口、离线同步）

**交付物**：技术选型报告、架构设计说明书、数据库设计、编码规范、评审记录
**关键节点**：第 3 周完成架构评审；实现期每周至少 1 次代码评审
**技能**：全栈能力，熟悉一款后端框架 + 数据库设计

---

### R4 前端开发（FE）

**核心职责**

- 实现 20+ 张量表的录入界面（本项目工作量最大的部分）
- 实现通用表单引擎（若采用配置化方案）或逐表页面（若采用硬编码方案）
- 实现特殊控件：计时器、图卡查看器、语音读题/听写、触摸屏适配、手写签名
- 对接后端接口，处理表单校验与错误提示

**交付物**：前端源码、页面清单对照表、组件文档
**关键节点**：第 4 周完成 3 张样板表（SCD-A 节、MMSE、ADAS-cog）→ 评审通过后批量复制
**风险**：工作量最重，TA 与 BA 在设计阶段结束后需投入支援

---

### R5 后端与数据（BE）

**核心职责**

- 后端接口开发（受试者主档、访视、量表实例、条目作答、统计查询）
- 数据库实现与迁移脚本
- 角色权限与登录
- 数据导出（Excel/CSV）、多中心数据合并（若确认要做）
- 离线同步（若确认要做）

**交付物**：后端源码、接口文档（OpenAPI）、数据库脚本、部署说明
**关键节点**：第 4 周完成受试者 + 量表实例两条主链路接口

---

### R6 测试与质量（QA）

**核心职责**

- 编写《测试计划》《测试用例》（覆盖每张量表的校验规则 V-01～V-10）
- 执行单元测试监督（开发自测）+ 集成测试 + 系统测试 + 验收测试
- 缺陷跟踪（提单、复现步骤、严重级别、回归验证）
- 编写《测试报告》，组织验收演示

**交付物**：测试计划、测试用例集、缺陷清单、测试报告、验收记录
**关键节点**：需求评审时就介入写用例；每张量表交付即测，不等到最后
**技能**：细心、熟悉等价类/边界值；会用 Postman 或浏览器开发者工具

## 3. 阶段 — 角色工作量配比

| 阶段              | PM     | BA     | TA     | FE     | BE     | QA     |
| ----------------- | ------ | ------ | ------ | ------ | ------ | ------ |
| 问题定义 / 可行性 | ●●● | ●●   | ●●   | ○     | ○     | ○     |
| 需求分析          | ●●   | ●●● | ●     | ●     | ●     | ●●   |
| 总体 + 详细设计   | ●●   | ●●   | ●●● | ●●   | ●●   | ●     |
| 编码与单元测试    | ●     | ●     | ●●   | ●●● | ●●● | ●●   |
| 综合测试          | ●●   | ●     | ●     | ●●   | ●●   | ●●● |
| 交付与维护        | ●●● | ●●   | ●     | ●     | ●     | ●●   |

（●●● 主责 / ●● 主要参与 / ● 参与 / ○ 基本不参与）

**人力调配建议**：设计阶段结束后，BA 转做前端页面验收与用户手册，TA 投入 30% 支援前端；测试用例在需求阶段就开始写，避免测试期堆积。

### 3.1 迭代工时预算（按 8 周版）

假设每人每周 8–10 小时：2 周迭代约 16–20 小时/人，I4、I5 各 1 周约 8–12 小时。各迭代预算如下（单位：小时）：

| 迭代                  | R1 PM | R2 BA | R3 TA | R4 FE | R5 BE | R6 QA | 小计  |
| --------------------- | ----- | ----- | ----- | ----- | ----- | ----- | ----- |
| I1 需求与可研（2 周） | 16    | 18    | 16    | 14    | 14    | 16    | 94    |
| I2 设计与骨架（2 周） | 14    | 20    | 20    | 20    | 20    | 14    | 108   |
| I3 核心闭环（2 周）   | 14    | 16    | 18    | 20    | 20    | 18    | 106   |
| I4 剩余与导出（1 周） | 10    | 10    | 10    | 12    | 12    | 12    | 66    |
| I5 测试与验收（1 周） | 14    | 8     | 8     | 8     | 8     | 12    | 58    |
| **合计**              | **68** | **72** | **72** | **74** | **74** | **72** | **432** |

### 3.2 均衡规则

1. **迭代内基线**：每人每迭代不低于 14 小时（I4、I5 各不低于 8 小时），低于基线须在周报说明原因；
2. **偏差检查**：任一成员实际工时与迭代均值相差超过 ±25%，PM 在当周周报标注并调整下阶段任务；
3. **前后端不背锅**：R4/R5 编码量再大，也不通过长期加班解决，而是砍 P1/P2 范围（见《迭代计划 v3.0》第 3 节）；
4. **文档工作量计入**：写文档、画原型、写用例都是正式工作量，不允许「程序员只写代码、非程序员只写字」的割裂；
5. **PM 不空转**：R1 的工时用于计划/周报/配置/变更/验收材料，不足时承担演示环境搭建与部分测试执行。

## 4. 协作规范

### 4.1 仓库结构（monorepo）

```
repo/
├── docs/                  # 全部文档（需求/设计/测试/交付）
│   ├── 01-需求/
│   ├── 02-设计/
│   ├── 03-测试/
│   └── 04-交付/
├── frontend/
├── backend/
├── assets/scale-cards/    # 量表刺激图卡（注意版权与保密）
├── scripts/               # 数据导入导出、构建脚本
└── README.md
```

### 4.2 分支策略

| 分支                      | 用途       | 规则                                          |
| ------------------------- | ---------- | --------------------------------------------- |
| `main`                  | 可交付版本 | 只接受 `develop` 的合并，每次合并打 tag     |
| `develop`               | 集成主线   | 每日可运行                                    |
| `feature/<模块>-<简述>` | 功能开发   | 从 `develop` 拉出，完成后 PR 回 `develop` |
| `fix/<缺陷号>-<简述>`   | 缺陷修复   | 同上                                          |
| `release/<版本>`        | 发布准备   | 只修缺陷，不加功能                            |

### 4.3 提交规范

`<类型>(<范围>): <简述>`，类型：`feat` / `fix` / `docs` / `refactor` / `test` / `chore`
例：`feat(mmsе): 完成 MMSE 30 题录入页与自动计分`

### 4.4 评审机制

| 评审     | 时机              | 参与人                       | 产出               |
| -------- | ----------------- | ---------------------------- | ------------------ |
| 需求评审 | 需求基线冻结前    | 全员 + 老师                  | 评审意见表、修订版 |
| 设计评审 | 架构/数据库定稿前 | 全员                         | 决策记录（ADR）    |
| 代码评审 | 每个 PR           | 至少 1 人（TA 必审核心模块） | PR 评论            |
| 测试评审 | 用例定稿前        | BA + QA + TA                 | 用例基线           |
| 验收评审 | 交付前            | 全员 + 老师                  | 验收记录           |

### 4.5 例会

- **周一计划会 15 min**：本周目标、任务认领、阻塞项
- **周五复盘 30 min**：完成情况、问题、下周安排
- 会议纪要当天进 `docs/`，PM 维护

### 4.6 基线管理

| 基线                 | 冻结时机     | 变更方式               |
| -------------------- | ------------ | ---------------------- |
| 需求基线 v1.0        | 需求评审通过 | 变更单 → 评审 → 批准 |
| 设计基线 v1.0        | 设计评审通过 | 同上                   |
| 代码基线 v1.0（tag） | 综合测试通过 | 只允许缺陷修复         |

### 4.7 周报机制（每周向老师汇报）

课程要求每周向老师汇报一次进度。机制如下：

1. **频率与时限**：每周五 17:00 前，PM 按《周报模板-客户版-v1.0》汇总发出，抄送全组；周报 = 本周演示 + 本周产出 + 每人明细；
2. **内容要求**：每人一行，必须写清「本周任务、产出物链接、计划工时、实际工时、完成度、下周任务」；无产出的必须写明原因和阻塞；
3. **不准代写**：每人周五 16:00 前自行填写本人行，PM 只做汇总与点评，防止「一人写全组」；
4. **存档**：周报存 `docs/00-项目管理/周报/`，命名 `W<周次>-周报-v1.0.md`，作为课程过程材料；
5. **未达标处理**：连续两周实际工时低于 8 小时/周，或连续两周无产出物，由 PM 面谈并书面记录；第三周仍无改善，PM 向老师如实反映。

## 8. 工作量均衡与「摸鱼」防范

分工只写在纸上没有用，必须让「谁做了什么」每周可见、可查、可追溯。措施六条：

| 机制       | 做法                                                                    | 频率   |
| ---------- | ----------------------------------------------------------------------- | ------ |
| 任务认领   | 周一计划会每人认领本周任务，写进周报；不摊派模糊任务                    | 每周一 |
| 产出物锚定 | 每人每周至少 1 项可指认产出（commit / 文档路径 / 测试记录），周报附链接 | 每周五 |
| 按人汇报   | 周五演示每人 3–5 分钟讲自己做的部分，禁止「我们组做了……」            | 每周五 |
| 工时申报   | 每人报计划与实际工时，PM 统计分布；偏差 >25% 当周标注                   | 每周五 |
| 交叉评审   | 每周至少一次互评（代码或文档），评审意见记名归档                        | 每周   |
| 偏差升级   | 连续两周工时 <8h 或无产出 → PM 面谈并调整分工；第三周不改 → 报告老师  | 按需   |

**判定标准**：某成员连续两周「无产出物 + 无合理阻塞说明」，即认定为工作量不足，先调整任务，再按第 4.7 节升级。反过来，若某人长期 >10h/周，说明任务拆分不合理或范围过重，同样要调整——均衡是双向的。
